¿QUÉ HICIMOS EXACTAMENTE?
==========================

PARTE 1: DOCUMENTACIÓN DE ARQUITECTURA (ARCHITECTURE.md)
-------------------------------------------------------

Creamos un archivo llamado ARCHITECTURE.md que explica la arquitectura de tu 
aplicación usando diagramas Mermaid (que es un lenguaje para hacer diagramas 
en código).

¿Qué muestra el diagrama?

Nivel 1 (Contexto):
  - Quién usa la app: Los niños y sus tutores
  - Qué hace: Una plataforma educativa de finanzas
  - Con qué interactúa: Una base de datos remota en Render

Nivel 2 (Contenedores):
  - Frontend: El navegador con HTML, CSS y JavaScript
  - Backend: Django ejecutándose en Gunicorn (servidor Python)
  - Base de datos: PostgreSQL alojada en Render
  
Cada componente se conecta por HTTP/HTTPS y está claramente etiquetado.

Por si acaso, la arquitectura actual de tu app es:
- Monolítica: Todo corre en un servidor (sin separación en microservicios)
- Server-rendered: El servidor genera el HTML y lo envía listo
- Con progresión desbloqueada: Los niños deben completar un tema antes de 
  pasar al siguiente


PARTE 2: VISTAS RESPONSIVAS
----------------------------

Mejoramos 3 vistas principales para que se vean bien en cualquier dispositivo:

1. LOGIN.HTML (Página de inicio de sesión)
   ¿Qué cambió?
   - Rediseñamos el layout usando CSS Grid y Flexbox (sin Bootstrap)
   - Agregamos media queries para que se adapte a móviles pequeñas
   - En móvil (<576px): El formulario ocupa toda la pantalla, es más simple
   - En tablet (576-992px): Más espacio, mejor distribuido
   - En desktop (>992px): Centrado y con más padding alrededor
   - Mejoramos los colores y la tipografía para que sea más claro

2. REGISTRO.HTML (Formulario de registro)
   ¿Qué cambió?
   - Este es el más complejo: tiene varios pasos (usuario, datos, términos)
   - En móvil: Los pasos se muestran verticales, uno debajo del otro
   - En tablet y desktop: Se muestran lado a lado o en una columna ancha
   - El indicador de "pasos completados" se adapta al tamaño
   - Las contraseñas tienen un indicador de fortaleza visual
   - Aceptar términos es más fácil en móvil

3. INDEX.HTML (Dashboard - página principal después de login)
   ¿Qué cambió?
   - Antes: Las tarjetas de temas estaban en una lista plana
   - Ahora: Usamos CSS Grid que se adapta automáticamente
   - En móvil: 1 tarjeta por fila
   - En tablet: 2 tarjetas por fila
   - En desktop: 3 tarjetas por fila
   - Las tarjetas tienen efecto hover (se iluminan cuando pasas el ratón)
   - El progreso se ve más claramente en todos los tamaños


PARTE 3: VALIDACIÓN EN JAVASCRIPT
----------------------------------

Esto es lo más interesante y útil: ahora la app valida datos ANTES de enviarlos 
al servidor.

¿Por qué es importante?
- Es más rápido: No esperas a que el servidor responda
- Es más amigable: Ves los errores al instante
- Es más seguro: Evitas enviar datos mal formados

¿Qué validamos?

En LOGIN.HTML:
- Email válido (ejemplo: debe tener @ y un dominio)
- No dejes el campo vacío
- Si hay error, aparece un mensaje rojo debajo del campo

En REGISTRO.HTML (lo más completo):
- Email válido (con verificación en servidor también)
- Contraseña fuerte (mínimo 8 caracteres, una mayúscula, un número)
- Las dos contraseñas coinciden (si escribes diferente en "confirmar", sale error)
- Fecha de nacimiento válida (no puede ser en el futuro)
- Nombre del tutor es obligatorio
- Email del tutor es válido y único en la base de datos
- Debes aceptar los términos y dar consentimiento del tutor

¿Cómo se ve?
- Campo correcto: borde verde, checkmark ✓
- Campo con error: borde rojo, mensaje explicativo
- Campo que se está validando: muestra un indicador de carga
- Botón de envío: deshabilitado si hay errores

Creamos un archivo llamado validation.js que tiene todas estas reglas 
reutilizables. Así, si en el futuro quieres agregar más validación en otra 
página, solo incluyes este archivo y listo.


PARTE 4: BONUS - SEGURIDAD
---------------------------

Mientras implementábamos, notamos un posible problema: si alguien quisiera, 
podría usar la validación de email para descubrir qué correos están registrados 
(cuenta enumeración).

Solucionamos esto con "throttling": si intenta validar un email más de 10 veces 
en 60 segundos, le decimos "espera un momento". Así:
- Los usuarios legítimos no se molestan (es difícil llegar a 10 intentos)
- Los atacantes no pueden sondear la base de datos masivamente

¿CÓMO VERLO?

3. Corre: python manage.py runserver
4. Ve a http://localhost:8000/
5. Intenta registrarte y verás las validaciones en acción

- O usa las DevTools del navegador (F12 > responsive mode)

Los cambios están en la rama "copilot/feature-create-architecture-md" y se 
pueden hacer merge a main.

NOTA TÉCNICA
============

Si el profesor preguntas sobre la arquitectura:
- Es una arquitectura monolítica típica de Django
- Usa vistas server-rendered (no es un SPA)
- La BD está separada en Render, así los datos persisten
- Es escalable para este tipo de aplicación educativa

Si preguntas sobre validación:
- Usamos validación dual: cliente (rápido) + servidor (seguro)
- El servidor SIEMPRE valida, nunca confíes solo en JavaScript
- Agregamos throttling para evitar ataques de enumeración
- Los tests cubren casos exitosos y casos de error
